跨源请求（Cross-Origin Request）是现代 Web 开发中一个非常重要且常见的概念，它==涉及到浏览器的**安全模型**和 **CORS** 机制。==

---

## 什么是跨源请求？

当一个网页（比如运行在 `A.com` 上的前端代码）尝试去请求或访问一个**不同源**的资源（比如 `B.com` 上的 API 或图片）时，这个请求就被称为**跨源请求**。

这里的“源（Origin）”由三个部分共同决定：

|组成部分|示例|
|---|---|
|**协议 (Protocol)**|`http://` vs `https://`|
|**域名/主机 (Host)**|`www.example.com` vs `api.example.com`|
|**端口 (Port)**|`8080` vs `3000`|

导出到 Google 表格

如果你的请求地址与当前网页的地址，三者中**任何一个**不相同，那么它就是一次跨源请求。

- **同源示例：** `https://app.com:8080` 请求 `https://app.com:8080/data`
    
- **跨源示例：** `https://app.com` 请求 `http://app.com`（协议不同）
    
- **跨源示例：** `https://app.com` 请求 `https://api.app.com`（域名不同）

## 浏览器安全基石：同源策略 (Same-Origin Policy, SOP)

浏览器的安全模型基于一个核心原则：**同源策略（SOP）**。

### SOP 的作用

同源策略规定，一个源加载的文档或脚本不能与另一个源的资源进行交互。它的主要目的是**保护用户数据**：

> 想象一下，你打开了一个恶意网站（`bad.com`）。如果没有同源策略，`bad.com` 上的 JavaScript 就能自由地向你的银行网站（`mybank.com`）发送请求，读取你的账户信息，并发送给黑客。

### SOP 与跨源请求的关系

同源策略是严格的，但现代 Web 应用需要互相通信。因此，需要一种**安全机制**来“放宽”这种限制，这就是 **CORS**。

---

## 解决之道：跨源资源共享 (CORS)

**CORS (Cross-Origin Resource Sharing)** 是一种机制，它通过在 **HTTP 头部**中添加特殊字段，让服务器明确告诉浏览器：**“我允许来自某个或所有特定源的前端访问我的资源。”**

### CORS 的工作流程（简单请求）

当发起一个 **简单请求**（满足 GET/HEAD/POST 方法，且不使用特殊头部等条件）时，流程如下：

1. **浏览器添加 `Origin` 头部：** 你的前端（`A.com`）发出请求时，浏览器会自动在请求头中添加一个 `Origin` 头部，表明请求来自哪里。
    
2. **服务器检查并响应 `Access-Control-Allow-Origin`：** 服务器（`B.com`）接收到请求，检查 `Origin` 头部。如果允许该源访问，它会在响应头中添加：
    
    HTTP
    
```http
    Access-Control-Allow-Origin: https://A.com
```
    
3. **浏览器验证：** 浏览器收到响应后，检查 `Access-Control-Allow-Origin` 的值。
    
    - **如果匹配**（或值是 `*`），浏览器会将响应数据交给前端 JavaScript 代码处理。
        
    - **如果不匹配**，浏览器会拦截响应，并向控制台抛出 CORS 错误，前端代码将无法获取到响应数据。
        

### 预检请求（Preflight Request）

对于那些不符合“简单请求”条件的**复杂请求**（例如：使用了 PUT/DELETE 方法，或使用了自定义的请求头部），浏览器会进行两次通信：

1. **预检 (Preflight)：** 浏览器首先发送一个 **`OPTIONS`** 方法的请求给服务器。这个请求是为了**询问**服务器：“我将要发送一个复杂请求，你是否允许我使用特定的方法和头部？”
    
2. **服务器响应：** 服务器用一系列 `Access-Control-Allow-*` 头部（如 `Access-Control-Allow-Methods`、`Access-Control-Allow-Headers`）来回答。
    
3. **实际请求：** ==如果预检通过，浏览器才会发送真正的 GET/POST/PUT/DELETE 请求。如果预检失败，实际请求根本不会被发送。==
    

## 总结

跨源请求本身是 Web 的必然需求，但它受到 **同源策略** 的严格限制。**CORS** 是解决这一限制的**官方和安全**的机制，它要求**服务器端**通过 HTTP 响应头明确地授权哪些源可以访问其资源。如果你遇到跨域问题，**通常需要在提供资源的服务器端配置 CORS 头部**。
